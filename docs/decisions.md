# Decisions (ADR log)

Each entry: decision, why, what would change it. Research references point at `../RESEARCH.md` sections and `../research/*.md`.

## D1 — Warm pool + snapshot machinery, not fast boot
Nothing cold-boots a Linux userland in tens of ms; Firecracker's ~125 ms is the floor and every sub-100 ms vendor serves from a pool (RESEARCH §0, §2). The POC allocates from a warm pool and boots only to refill it. Snapshot restore with working-set prefetch is phase 2. Revisit if pool memory cost per developer machine becomes the binding constraint.

## D2 — Rust for guest-agent and qafas, Go for the control plane, React for UI
User decision. Rust gives one static musl binary that is both PID 1 in Firecracker and a container entrypoint, plus direct control of vsock, PTY, seccomp. Go keeps the control plane in the language of the user's other services and the Firecracker/E2B/Hypeman ecosystem. The data path never crosses the language boundary.

## D3 — Local backend is one warm Linux VM with containers inside, not a VM per task
Measured on the M5: exec into a running container inside the podman machine is ~107 ms via the CLI, of which ~63 ms is CLI + transport (research/05 §1.2). Apple `container` boots a VM per container in 0.7–0.9 s. VZ save/restore is gated behind a private Apple entitlement, so no fast restore exists on macOS. The POC reuses the existing `podman-machine-default` (applehv) and its REST socket. Revisit if nested virtualization on M3+ is measured cheap enough for per-task microVMs.

## D4 — Identical absolute path inside the sandbox
gemini-cli's trick. Deletes the path-translation layer that Gondolin needs. Podman: the machine already shares `/Users`, `/private`, `/var/folders` over virtiofs at the same paths. Firecracker: tar extracted at the same path. Builds on the virtiofs mount are slow (8–27× vs VM disk, research/05 §1.3); accepted for the POC, phase 2 moves the workspace to VM-native disk with sync.

## D5 — SQLite (modernc.org/sqlite) now; Turso/libSQL later if needed
Checked 2026-09-08: Turso DB (`tursodatabase/turso`), libSQL and `go-libsql` are all MIT. `go-libsql` requires cgo, which breaks the `CGO_ENABLED=0` static build, and its last push was April 2026. All three speak SQLite SQL, so with `database/sql` behind a `store` interface the swap is a driver change. Turso Cloud (hosted, proprietary) becomes relevant only for multi-node control planes needing embedded replicas.

## D6 — Secrets never enter the sandbox; credential injection is phase 2
The highest-leverage control in the research (RESEARCH §4 M6). The POC guarantees the negative half: pi keeps API keys on the host, containers get no host env, `~/.ssh`/`~/.aws` are not mounted. The positive half (sentinel → real token at the proxy for allowlisted hosts) needs TLS termination and a CA in the image; deferred with a documented gap.

## D7 — Egress enforced outside the sandbox, deny by default, no DNS inside
AgentCore's sandbox network was bypassed three times via DNS tunnelling (research/02 §3.8). Podman: sandboxes sit on an `internal` network whose only exit is the proxy container. Firecracker: nftables on the tap allows only tcp/3128 to the host proxy. The proxy resolves names; the sandbox never gets a resolver. Known limit: exfiltration through an allowlisted domain (pushing a branch to github.com) is not prevented.

## D8 — seccomp deny-list in guest-agent, Chromium exempt
Deny io_uring (Google kCTF: 60% of exploits), ptrace, process_vm_*, mount family, bpf, keyctl, userfaultfd, perf_event_open, module loading. Allow-lists break toolchains unpredictably; a deny-list costs microseconds and removes the worst surfaces. Chromium needs its own sandbox syscalls and is launched without the filter. `SBX_NO_SECCOMP=1` exists for debugging only.

## D9 — pi on the host, tools proxied into the sandbox (Design B)
Keeps LLM credentials out of the sandbox by construction and preserves the native TUI (research/06 §3). pi already exposes the `operations` seam and ships Gondolin as a reference. Whole-process-in-sandbox stays a documented alternative for when third-party extension tools must also be contained.

## D10 — `user_bash` fails closed
pi's runner swallows a throwing `user_bash` handler and runs the command on the host (issue #9068, closed not-planned; verified in `dist/core/extensions/runner.js:717-743`). The extension's handler is wrapped in try/catch and returns a synthetic `exitCode: 1` result. Gate B has a regression test.

## D11 — grep is re-implemented, not delegated
`GrepOperations` cannot redirect the search: `grep.js:144` always spawns host ripgrep. The extension overrides the `grep` tool by name and runs `rg` inside the sandbox via `POST /exec`. Upstream PR (`GrepOperations.search`) is worth filing.

## D12 — Browser inside the sandbox, one process per sandbox, one context per session
Measured: `chrome-headless-shell` launch 51 ms, new context 1 ms, new page 24 ms, ~80 MB per context (RESEARCH §3.4). Inside the boundary it obeys the egress policy. `--single-process` is never used (kills the renderer sandbox). Podman backend sets `SBX_CHROME_NO_SANDBOX=1` because the container already denies user namespaces; the VM plus container is the boundary there.

## D13 — `_snapshotForAI()` for accessibility snapshots
Same private Playwright API used by Playwright MCP; gives `e12`-style refs that `aria-ref=` locators resolve. `ponytail:` private API; fallback is `locator.ariaSnapshot()` plus client-side ref numbering.

## D14 — Build both musl targets from day one; x86_64 tested for real only on the remote box
Development is arm64-native on the M5. `make image-amd64` builds under qemu-user emulation inside the podman machine to prove the image; Firecracker itself needs KVM, so x86_64 execution is validated at Gate E on the Linux box.

## D15 — Repository scope
`sandbox/` is its own repository and product. The only reference to the user's llm-router project is copying its React/astryx scaffold files (listed in `docs/PLAN.md` §7) because the user wants the same UI library and theme setup.

## D16 — Three tiers, native first (2026-09-08)
Local agents from Anthropic and OpenAI use the OS process sandbox (Seatbelt; Landlock/seccomp/bwrap), not containers. We add a `native` tier as the default for trusted workspaces, keep `vm` (podman-in-VM) as the strong local tier and `remote` (Firecracker) for anything untrusted or multi-tenant. Selection is a fixed table (`crates/qafas/src/policy.rs`). Revisit if Apple ships a fast VM restore.

## D17 — One agent-core crate serves both the guest and the native tier
Same exec/pty/fs/browser handlers and the same telemetry, with a `Spawner` that either hardens in `pre_exec` (VM) or wraps in the OS sandbox (native). The protocol stays identical, so the harness cannot tell tiers apart except by the `isolation` field.

## D18 — Detection is layered, boundary-first
Boundary signals (proxy, sandbox denial reports, seccomp kills, cgroup) are authoritative; in-sandbox signals (process tracking, path watches, canaries, eBPF) are enrichment. seccomp switches from EPERM to KILL_PROCESS for syscalls that have no benign use, so an attempt is both stopped and visible as SIGSYS; io_uring keeps EPERM because libuv probes it.

## D19 — eBPF via bpftrace, not a custom program
`bpftrace -f json` with an embedded script gives exec/exit/open/connect/ptrace/mount tracepoints in ~40 lines and no cross-compiled BPF object. Linux with BTF only (remote tier, native-Linux hosts). Replace with an aya program only if bpftrace's overhead is measured to matter.

## D20 — Traces are OpenTelemetry-shaped, storage stays ours
SQLite events remain the source of truth; the control plane maps a session to an OTLP trace (`protocol.md` §1.2) for its own waterfall view and for optional push to any OTLP collector. No OTel SDK dependency.

## D21 — Tools are requested, probed and reported, never silently installed
`tools:["node@22"]` resolves against the host (native) or an image template (vm/remote); the reply lists `missing_tools`. On-demand installation inside the sandbox is phase 3.

## D22 — The harness, not the model, extends egress
`egress_allow` on the create request comes from harness configuration. A model cannot call `POST /sandboxes`; scoped tokens cannot create sandboxes.

## D23 — Idle sandboxes sleep, and wake on use (v4)
`auto_stop_secs` applies on every tier (native: kill the shim, workspace is the host dir; vm: `podman stop`; remote: Firecracker snapshot) with a daemon default (`SBX_AUTO_STOP_SECS`, 30 min), and `auto_delete_secs` (`SBX_AUTO_DELETE_SECS`, 24 h) is the grace period before a stopped sandbox is destroyed. A request that reaches a `stopped` sandbox starts it first, in qafas, once, rather than in every SDK and harness. `paused`/`archived` remain explicit and answer 409. Long-running sandboxes are reported through the alert pipeline (`sandbox.long_running`) instead of a parallel notification system: one store, one page, one metric, one Prometheus rule.

## D24 — Monitoring: hand-rolled Prometheus text, the control plane is the only scrape target, Langfuse via OTLP
Both binaries render Prometheus text by hand (no client library, D20 spirit). Prometheus discovers targets from `GET /api/prometheus/targets` and scrapes every worker through `GET /api/hosts/{id}/metrics`, so the monitoring stack needs one network path (to the control plane VM) and the workers' `SBX_TOKEN`s never leave the control plane. Grafana dashboards and alert rules ship as files under `deploy/monitoring/`. Trace export is one OTLP/HTTP pusher with a stored, admin-editable destination; Langfuse is that pusher pointed at Langfuse's OTLP receiver with basic auth, not a second exporter. Profiling is Go `net/http/pprof` on the control plane; qafas profiling is `perf`/`samply` on the host (ponytail: `tokio-console` is the upgrade if async stalls ever need attribution).

## D25 — One pooled runtime per host, Firecracker first, one vocabulary
A host runs one pooled backend; when a Linux host could serve both podman (`vm`) and Firecracker (`remote`), `remote` wins and `vm` is dropped from its capabilities with a warning. Hosts advertise what they can actually do. The product's default runtime is Firecracker: the control plane resolves `auto` as `remote` > `vm` > `native`, and the dashboard offers only the runtimes the live fleet advertises, Firecracker preselected. The wire values `native|vm|remote` are frozen (rows, events, metric labels, dashboards); the product names `process|docker|firecracker` are input aliases and the only labels a person sees. Placement is by tier, snapshot presence and key limits; nothing falls back silently and daemon errors reach the client unchanged.

## D26 — Hosts, templates, sandboxes: the operator workflow (v4c)
Three nouns, in the order an operator meets them.

**1. Host.** The installer (`deploy/worker/install.sh`, retired 2026-10-06 for the packages; now the operator) runs `qafas doctor --json` on the machine before anything else and prints what it found (KVM, Firecracker, podman, process sandbox, bpftrace, huge pages, CPU, memory) and the runtimes those allow. The operator confirms or narrows the runtimes (`SBX_TIERS`); the daemon can never serve more than the capabilities allow, and Firecracker wins over Docker on a host that could do both (D25). At registration the host sends its capabilities (`HostRegister.caps`); the Hosts page shows them next to the served runtimes, so "why does this host not offer Docker" is answered on the page. Runtime tags are the host's advertised tiers; there is no separate label to keep in sync.

**2. Template.** What the API calls a snapshot the UI calls a template: a named image (from a registry reference or a Dockerfile) or a checkpoint of a live sandbox, built for one runtime. A template carries its runtime (`CreateSnapshotReq.runtime`, `SnapshotInfo.runtime`): the control plane builds it on the hosts of that runtime only, and a checkpoint is built only on the host that owns the sandbox. Firecracker templates get a memory capture and per-template warm counts (D25 phase 4b); Docker templates are podman images. `base` exists on every host.

**3. Sandbox.** Create picks a runtime, then a template of that runtime (only active ones, `base` first), then optional details. A Dockerfile can be pasted right there: the dashboard builds a template named after the sandbox, waits for it to become active with progress, then creates. The workspace is optional everywhere: Firecracker sandboxes receive files by upload, Docker and Process sandboxes get an empty working directory of their own unless a host directory is named, in which case it is mounted at the identical path. A host path is only meaningful for hosts on the same machine as the client, so the dashboard shows that control only for the Process and Docker runtimes and never requires it.

## D27 — Sizes: named or custom, enforced at the boundary, placement is tier + fit (v5)
A sandbox carries `SandboxLimits {cpus, mem_mib, disk_mib, pids}` from a named size (`micro|mini|medium|high`, `SBX_SIZES` overrides) or a custom triple; `medium` is the pre-v5 unit, so nothing changes for callers that say nothing. Limits are set at create and re-applied when a pooled sandbox is handed out (one pool, not one per size); they are enforced where the workload cannot reach — cgroup v2 on `vm`, an in-guest cgroup written by the root guest agent plus a host `cpu.max` on `remote`, a cgroup leaf on Linux `native`, and qafas's own watchdog on macOS `native` (reported as `enforcement: daemon`; CPU uncapped there, documented). API keys bound sizes (`allowed_sizes`, `max_*`) and violations are refused, never clamped. The control plane keeps Σ limits per host (`committed`) and refuses a host once `committed + requested > caps × overcommit` (`SBX_OVERCOMMIT_*`, default 1.0) — placement stays one query over `hosts`+`sandboxes`, it just gained two sums; the winner is still the most free warm pool. This amends D25's last sentence: placement is by tier, snapshot presence, key limits **and fit**. Usage (`SandboxInfo.usage`, `sbx_sandbox_*` gauges) is sampled at the same boundary. Deliberate ceilings: scratch on `vm`/`remote` is RAM-backed so `disk_mib` never exceeds `mem_mib` in practice; a pooled `vm` container keeps its creation-time tmpfs size; Firecracker guests keep the template's RAM/vCPU (sizes above template RAM are refused; a balloon is the upgrade); the bind-mounted workspace is unlimited.

## D28 — The debt pay-down (2026-09-18): the daemon's record is the record, usage is pushed
Every `ponytail:` marker was either upgraded or rewritten as `design:` (a recorded limit nobody intends to change); `/ponytail-debt` is the ledger of intent from now on. Two additive contract changes came out of it (v5.1): the daemon's `201` carries `info` (its own `SandboxInfo` — name, labels, resolved timers, enforcement) so the control plane stores what the daemon holds instead of re-deriving defaults from the request; and the guest agent pushes `sandbox.usage` every 2 s while an exec is live (plus once at exec end), so `SandboxInfo.usage` and the control-plane row are ≤ 2 s old during a run, with the 5 s pull / 10 s heartbeat kept for idle sandboxes. Structural changes that follow from it: the workload runs in a sibling cgroup leaf (`sbx/work`, agent in `sbx/agent`) so an OOM can never pick the agent; every exec is its own session (`setsid`), which is what lets a stuck session command die alone and fixed PTY execs; the macOS watchdog enforces `pids`; process attribution on the remote tier resolves lineage → session → pgid and counts what it cannot attribute instead of dropping it; events the control plane will not take are spooled to `<state_dir>/events.spool` (64 MiB) and replayed on the next success or every 30 s. Not done on purpose: proxy keep-alive to upstream (clients reuse one proxy connection for different hosts, so a byte relay would answer from the wrong socket — needs response framing), per-key pool locks (no await under the lock, nothing to contend), the Firecracker balloon, per-size pools, a macOS CPU cap.

## D29 — Installable on a Linux server (2026-09-20): packages, images, and what rootful podman needed
Three packages per release, built by `scripts/package.sh` with nfpm from the same static binaries the tarballs ship: `qafas` (worker), `qafas-controlplane`, `qafas-cli` — `.deb` for Debian/Ubuntu/Mint, `.rpm` for RHEL/Rocky/Alma/Fedora, arm64 and amd64. Installing is the setup: the control plane's three tokens and the worker's token are minted in `postinstall`, the units are enabled and started, and a worker installed beside a control plane joins it in either order (`/usr/libexec/qafas/join-local-controlplane`). Config files are conffiles (yours across upgrades); the guest image for the version rides in a unit drop-in (`SBX_TEMPLATE_IMAGE`) and in `/usr/share/qafas/templates.json`, so an upgrade moves the image with the daemon — they must match, because the egress proxy runs the `qafas` binary from the image. The daemon pulls the image when the host has never seen it; an air-gapped host `podman load`s the release tarball, tagged with the same registry name. Three container images (`controlplane`, `qafas`, `sbx`) and `deploy/docker/compose.yml` give the Docker route; the worker image drives the host's podman over its socket, so the sandboxes are host containers on the same path as the packages. Tried and rejected: the worker running its own podman inside a privileged container — the nested podman cannot apply cgroup limits without controller delegation, and with `--cgroupns=host` its crun attaches a device program to the host's root cgroup (every process on the host lost `/dev/fuse` until a reboot). Validated on Ubuntu 24.04 and Rocky 9 in Lima VMs.

Running the `vm` tier as root on Linux — which is what a service is — exposed three things the podman machine on macOS had hidden. (1) The sandbox network is `internal`, so netavark makes no DNAT: the published `127.0.0.1` port that gvproxy forwards on macOS leads nowhere. Rather than give the host an address on that bridge (a sandbox could then reach host services), the daemon reaches guest agents through a policy-free CONNECT relay on the egress proxy container, the one thing already dual-homed on purpose; the relay serves only peers outside the sandbox subnet, only for targets inside it, and is chosen by probing at start. The connector carries the container name and a name→address table the backend keeps current across stop/start, so nothing above the backend changed. (2) `keep-id` is a no-op under rootful podman: the sandbox is the host's real uid 1000. The workspace is therefore mounted as an idmapped mount (`idmap=uids=<owner>-1000-1`): the owner is uid 1000 inside, writes land as the owner — the macOS semantics. The image's `/root` is `0711` so a `/root/<dir>` workspace is reachable. (3) SELinux-enforcing hosts refuse the bind mount unless the tree is relabelled or the container is unconfined; the sandbox container runs with `label=disable` because `:z` is a permanent change to the operator's files (security.md M42 records the gap). Also from this work: the egress policy reaches the proxy as content (`SBX_POLICY_JSON`), not a host path, and the daemon finds the system podman socket on Linux without `SBX_PODMAN_SOCK`.

## D30 — Template security grades: a linPEAS-style checklist, not linPEAS (2026-09-24)
The user asked whether Qafas needs something like linPEAS to tell whether a sandbox can be compromised, with a score per template. The boundary is outside the sandbox (uid 1000, empty capability set, `no_new_privs`, seccomp, internal network), so a host privilege-escalation enumerator run inside reports mostly noise — setuid binaries and kernel exploit suggestions are moot there — and shipping an attacker toolkit into every image is wrong for an air-gapped product. What does vary is the template: a user's image or Dockerfile can put a model API key in `ENV`, bake credentials in, add set-id programs or file capabilities, or drift from what the boundary assumes. So: one POSIX script (`images/probe/scan.sh`, embedded in `qafas`) run through the ordinary exec path in a throwaway sandbox of the template on the host's own runtime; two classes of check — `boundary` (the tier's promise; one failure is grade `F`) and `hygiene` (the image's content; each failure lowers the grade); a letter, not a number, because a number invites comparisons the checks cannot support. The one policy: `trust: untrusted` cannot use an `F` template (`409`); trusted work can, and sees the grade. Scans run after every build before the row goes active, for `base` once per image digest at start, and on demand (`202`, background — the control plane's forwarding client has a 10 s timeout and a Firecracker boot plus scan can exceed it). The scan sandbox is not a sandbox anyone holds: no events, so the probe itself raises no alerts; the one check that would have (a metadata request through the proxy) was dropped because the proxy's private-address refusal is enforced and unit-tested, and the direct request still tests the network boundary. Grades are per host and runtime: a Firecracker rootfs is a `podman export`, which carries neither `ENV` nor xattrs, so the same Dockerfile grades `F` on `vm` and `C` on `remote` — the scan grades what the sandbox actually gets. Not done: CVE scanning (a vulnerability DB in the air gap), scoring live sandboxes (their posture is derivable from the record; their behaviour is what the boundary detections watch).

## D31 — Internal mirrors are an operator's private-range allowlist, not a policy override (2026-10-06)
An air-gapped datacenter has no public addresses: its package mirrors (Nexus, Artifactory, a PyPI or npm proxy) sit on RFC1918, and the egress proxy refused every private address whatever `allow` said, so a sandbox could install nothing. Options were to drop the private-address rule when a name is allow-listed, or to let the harness name ranges per sandbox. Both hand the internal network to whoever writes the request. Chosen: `allow_private_cidrs` in the **host** `egress.json` only — a name must still be in `allow`, the address must be inside a listed range, and only RFC1918 and unique-local can be opened at all (loopback, link-local and CGNAT carry metadata endpoints and stay shut). `egress_allow` on a create request keeps adding names only. Contract v5.3, additive (security.md M44).

## D32 — The vm tier also runs on Docker Engine, as a dialect of the podman backend (2026-10-06)
The "Docker" quick start still needed podman on the host, because the worker drives the libpod API; most servers that would host a pilot have Docker and not podman, and podman-in-Docker was already rejected (D29). Options were a second backend, or one backend speaking two dialects. The calls are the same dozen (containers, images, networks) with different request shapes, and every caller keys on the backend's name for the image model they share, so the podman backend learned Docker's dialect, chosen once at start from `/_ping` (podman answers with `Libpod-Api-Version`). Two things do not translate. Docker has no idmapped bind mounts, so a Docker sandbox runs as its workspace's owner, and a root-owned workspace is refused rather than run as root. Docker always injects an embedded resolver on a user-defined network; on an `internal` one it forwards nothing since 26.0, so it resolves only sandbox-network names — a recorded deviation from D7 (security.md M45), with Docker < 26 refused. Template builds on the vm tier moved from the podman CLI to the socket's Docker-compatible endpoints (both runtimes serve them), which also made templates work in the distroless worker container, on either runtime.

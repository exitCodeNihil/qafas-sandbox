## Escape review (2026-09-08)

`make escape TIER=native` and `TIER=vm`. Probes: credential reads (real and via symlink), write outside the workspace, git hook write, `/proc/1/environ`, host env leakage, direct network bypassing the proxy, cloud metadata, DNS exfiltration, ptrace, mount, user namespaces, container sockets, setuid `sudo`, io_uring, fork bomb, killing PID 1. Result on both tiers: nothing escaped; every probe that must alert did. Known limits found and accepted:

- **VM tier, direct network bypass**: there is no route, so the attempt fails silently; no alert without eBPF (remote tier). The native tier reports it (`sandbox.denied` high on `network-outbound`).
- **VM tier, processes shorter than ~25 ms** are not individually reported (their exec/exit is still inside the parent exec's span).
- **macOS `sudo`**: Seatbelt refuses setuid execs with no log line; detection is by command line (`setuid.exec`).
- **Seatbelt report latency** is about a second; the denial itself is synchronous.

Monitoring tiers (RESEARCH §4): tier 1 = harness gate, qafas proxy events, egress proxy, cgroup; the POC UI shows tier-1 data only. In-guest eBPF and PTY recording are phase 2.

TLS caveats worth stating: the POC's default certificate is self-signed and trusted on first use — the control plane pins whatever the host presents at registration, so the guarantee is only as strong as `SBX_HOST_TOKEN` and the network at that first moment. `SBX_CA_FILE` (an internal CA) removes that window and is what production should use. `SBX_TLS_INSECURE=1` disables verification entirely and exists for debugging only. The Node SDK pins by adding the verified certificate to the process CA set, so a pin applies process-wide rather than per connection.

Closed, from the client→sandbox data path audit (2026-09-09): the vm tier's guest-agent port is published on `127.0.0.1` and gvproxy forwards it to the Mac, so any local process that found the port used to get `/exec` and `/fs/*` in that sandbox, including the bind-mounted workspace. A published TCP port cannot be closed the way M39 closes the native tier's `agent.sock` (`0700`), so M40 puts a per-sandbox secret in front of it instead. The remote tier was never affected (vsock, M37). Residual on the vm tier: the guest-agent there runs as uid 1000, the same uid as every exec, so reaching it was never an escalation.

Known gaps to state plainly: exfiltration through an allowlisted domain; the workspace is live on both local tiers, so sandboxed code can write files the host later executes (M11 detects the common paths, does not prevent); no TLS termination so no credential injection; the native tier shares the host kernel (Seatbelt is a policy boundary, not a virtualisation boundary — that is why untrusted workspaces never get it); the podman backend shares one VM kernel across concurrent local sandboxes.
